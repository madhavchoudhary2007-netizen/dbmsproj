# ApexGrid shared contracts

## Ownership and wire format

- IDs are UUID strings. All external timestamps are UTC ISO 8601 strings with `Z`; PostgreSQL uses `timestamptz`.
- PostgreSQL owns users, competition, sessions, incidents, penalties, results, standings and pit operations. MongoDB owns telemetry documents only. Mongo documents refer to PostgreSQL UUIDs as strings.
- API root is `/api`. JSON errors have `{ "detail": "human readable message" }`. Lists are bounded with `limit` (default 50, maximum 200) and `offset`.
- Roles: `ADMIN`, `STEWARD`, `PRINCIPAL`, `DRIVER`. `ADMIN` can manage all; `STEWARD` can decide incidents; `PRINCIPAL` can request pit reservations only for an assigned team; telemetry ingest requires `ADMIN` or `STEWARD` and an active session; read access requires login.
- Session state: `SCHEDULED`, `ACTIVE`, `PAUSED`, `COMPLETED`, `CANCELLED`. Eligibility: `ACTIVE`, `RACE_BANNED`. Tire compounds: `SOFT`, `MEDIUM`, `HARD`, `INTERMEDIATE`, `WET`. Incident state: `OPEN`, `APPROVED`, `REJECTED`. Session types: `PRACTICE`, `QUALIFYING`, `RACE`.

## Relational model

All entity primary keys are UUID. Table names are plural snake case. `users(id,email,password_hash,full_name,role)`, `teams(id,name,principal_user_id)`, `drivers(id,user_id,licence_number,number,eligibility)`, `team_memberships(id,driver_id,team_id,start_date,end_date)`, `championships(id,name,season)`, `circuits(id,name,country,length_km)`, `race_events(id,championship_id,circuit_id,round_number,name,start_date)`, `race_sessions(id,event_id,session_type,state,scheduled_at,started_at,ended_at,total_laps,safety_car)`, `incident_reports(id,session_id,driver_id,lap,description,state,reported_at,decided_by,decision_notes)`, `penalties(id,incident_id,driver_id,points,time_seconds,grid_places,created_at)`, `penalty_points(driver_id,season,points)`, `session_results(id,session_id,driver_id,position,lap_time_ms,pole,fastest_lap,classified)`, `driver_standings(championship_id,driver_id,points,wins,podiums,rank)`, `pit_boxes(id,event_id,number)`, `pit_reservations(id,pit_box_id,session_id,team_id,driver_id,allocation_source,starts_at,ends_at,status)`. `driver_id` is nullable for legacy bookings; `allocation_source` is `MANUAL` or `AUTOMATIC`. Session `total_laps` is an integer from 0 through 72; the idempotent migration caps existing values above 72.

Important invariants: one result per `(session_id,driver_id)` and one classified result per `(session_id,position)`; team memberships cannot overlap for a driver; PostgreSQL enforces session transition and timestamp rules; unique driver licence; unique event round within championship; all counters nonnegative; reservations require `ends_at > starts_at`. Incident laps are constrained to the owning session's configured lap range. A partial unique constraint allows only one active reservation for a driver in a session, alongside box/window conflict protection. An approved incident creates at most one penalty. PostgreSQL trigger on official penalty insert updates seasonal `penalty_points`; total >= 12 sets driver `RACE_BANNED`. Official penalty rows are immutable: database triggers reject updates and deletes. PostgreSQL `recalculate_standings(championship_id)` uses an explicit cursor, scoring `[25,18,15,12,10,8,6,4,2,1]`, +1 pole and +1 fastest lap; it upserts championship totals and ranks. Pit reservation transaction locks the target `pit_boxes` row with `SELECT ... FOR UPDATE`, rechecks overlap, inserts, and commits.

## REST

- `POST /api/auth/login` `{email,password}` -> `{access_token,token_type:"bearer",user:{id,email,full_name,role}}`; `GET /api/auth/me` -> user.
- Admin user management: `GET /api/users`, `GET /api/users/{id}`, `POST /api/users` `{email,full_name,password,role}` and `PATCH /api/users/{id}` (name/email/role/optional password), `DELETE /api/users/{id}` when unreferenced. Responses exclude `password_hash`.
- CRUD resources use conventional `GET /api/{resource}`, `GET /api/{resource}/{id}`, `POST /api/{resource}`, `PATCH /api/{resource}/{id}`, `DELETE /api/{resource}/{id}` for `championships`, `circuits`, `teams`, `drivers`, `events`, `sessions`; mutation privileges are admin unless specified. New events receive pit boxes 1–4. Deletes of referenced official records return 409. Responses include IDs and relevant joined display fields.
- `GET /api/drivers/{id}/memberships` and `GET /api/teams/{id}/memberships` return dated membership history; `POST /api/team-memberships` `{driver_id,team_id,start_date,end_date}` and `PATCH /api/team-memberships/{id}` manage it (admin).
- `POST /api/sessions/{id}/action` `{action:"start"|"pause"|"resume"|"finish"|"reset"}` -> session. Explicit reset clears that session's telemetry and results and recalculates standings; sessions with official penalties cannot be reset. `started_at` and `ended_at` are writable only through lifecycle actions, not generic session writes.
- Driver eligibility changes only through the official penalty trigger. Generic driver writes do not accept `eligibility`. Session creation defaults to `SCHEDULED`; lifecycle changes use `/action`.
- `GET /api/sessions/{id}/results` adds `provisional: boolean` to each result row when that session has a historical positive time or grid penalty; `POST /api/sessions/{id}/results` accepts an array of `{driver_id,position,lap_time_ms,pole,fastest_lap,classified}`. `POST /api/championships/{id}/recalculate` invokes PostgreSQL routine; `GET /api/championships/{id}/standings` reads persisted rows and adds `provisional: boolean` when a completed race in that championship has a historical positive time or grid penalty. The flag means the stored classification or standings may not reflect the sanction; it does not change ranks or points.
- `GET/POST /api/incidents`; `POST /api/incidents/{id}/decision` `{approve,notes,points,time_seconds,grid_places}` -> incident plus current driver point/eligibility state. Decision is atomic and always returns driver state, including rejected decisions and approved decisions with zero penalty. Positive `time_seconds` or `grid_places` currently return 422 with guidance because official race elapsed and starting-grid rules do not yet apply them; existing stored sanctions are preserved under ADR-003.
- `GET /api/pit-boxes?event_id=`; `GET /api/pit-reservations?session_id=` returns enriched rows with `box_number`, `team_name`, `driver_id`, `driver_name`, `driver_number`, and `allocation_source` (driver fields can be null on legacy bookings). `POST /api/pit-reservations` `{pit_box_id,session_id,team_id,starts_at,ends_at}` creates an explicit manual box/time booking. `POST /api/pit-reservations/auto` accepts `{session_id,team_id,driver_id?}` and allocates the earliest available event box/window; omitted driver deterministically selects the first eligible team driver without an open stop. It returns the enriched reservation row, including assigned `box_number` and driver. It requires an active/paused session and event pit boxes; no boxes or conflicting allocation returns HTTP 409. The stop duration follows the live simulator rate. Admins/stewards may book any team; principals may book only their own team. `PATCH /api/pit-reservations/{id}` `{status:"CANCELLED"|"COMPLETED"}` closes an active reservation; admins/stewards or the owning principal may close it.
- `GET /api/sessions/{id}/pit-strategy` (authenticated) returns `{session_id,session_state,source,strategy,historical_summary}`. Each driver strategy row includes current lap, tire compound/age/wear, recommended stop lap and window, decision status/reason, assigned box, and recorded stops. `historical_summary` counts completed stops and lists their laps per driver. Generated active races expose live automatic decisions; completed or non-generated sessions expose recorded history without future recommendations. Pit Wall polls this endpoint and displays automatic reservations read-only.
- `POST /api/telemetry/ingest` normalized telemetry packet -> HTTP 202 accepted packet. An exact retry of any persisted packet for the same session/driver returns its original packet ID without another insert or live event, even after newer packets; a nonidentical older or conflicting packet returns HTTP 409 with an out-of-order detail (ADR-005). `GET /api/telemetry?session_id=&driver_id=&limit=` -> recent MongoDB documents. `GET /api/analytics/drivers` accepts championship/season/circuit/driver/team filters plus `limit` and `offset` pagination.
- `POST /api/sessions/{id}/simulate` `{action:"start"|"pause"|"resume"|"stop"|"reset",cars?:integer,rate_hz?:number}` -> `{session_id,state,cars,rate_hz}`. Simulation is a telemetry provider; only admin/steward can control it. Reset requires the session to be paused and clears stored telemetry and results; a new simulation start after stop begins with clean measurements. External telemetry ingest requires an authorized token.
- `GET /api/dashboard` -> active context/counts; `GET /api/health` -> per service health.
- DBMS endpoints under `/api/dbms` require admin: `GET /schema`, `/indexes`, `/explain?query=leaderboard|licence`, `/locks`, `/telemetry`, `/polyglot`; `POST /constraint-demo`, `/transaction-demo`, `/lock-demo`, `/recalculate`. `transaction-demo` performs a real savepoint write and rollback. `lock-demo` runs two conflicting PostgreSQL pit reservations and reports measured lock wait plus actual commit/rejection outcomes. Each endpoint executes real database operations and reports actual results.

## Live telemetry

Normalized packet: `{session_id,driver_id,ts,lap,sector,elapsed_ms,lap_time_ms,sector_ms:[...],position,speed_kph,throttle_pct,brake_pct,tire_compound,tire_age_laps,tire_wear_pct,tire_temp_c:[...],pit_state,pit_reservation_id,pit_box_number,pit_team_id,pit_starts_at,pit_ends_at}`. Percentages are 0..100 and `lap` is bounded 0–72. A simulator tick advances one sector and increments the lap only after sector three; a configured race completes on the first sector-three packet at its lap limit. Generated races schedule automatic stops at compound-specific tire-age targets, mark only the assigned driver as `IN_PIT`, then reset tire age/wear and change compound; pit state and reservation metadata are included in telemetry/timing updates. `GET /api/sessions/{id}/live` returns current snapshot. `WS /api/ws/sessions/{id}` authenticates with offered subprotocols `["apexgrid.jwt", access_token]`, accepts `apexgrid.jwt`, and emits `{type:"session.state"|"timing.update"|"telemetry.sample"|"pit.update"|"incident.update",ts,session_id,data}`. Clients reconnect and fetch a fresh snapshot. Simulator and external ingest both publish this shape; the frontend never reads simulator internals.

## Generated live demo races

- `demo_races(session_id,event_id,created_at)` identifies only system-generated races. `demo_race_entries(session_id,driver_id,pace_offset_ms)` identifies the drivers owned by that generated race. These markers keep deletion scoped to generated data; seeded or manually created races are never removed by the demo deletion endpoint.
- `GET /api/demo-races` (authenticated) returns generated race rows with `session_id`, `event_id`, `event_name`, `circuit_name`, `state`, `total_laps`, `car_count`, `simulation_state`, and `created_at`, newest first.
- `POST /api/demo-races` (admin/steward) takes `{cars?: integer}`. Omit `cars` for a randomly selected field size from 8–16; explicit values must be 6–20. It atomically creates an event and an active race session under the separate ApexGrid Live Demo championship, plus four pit boxes and fresh fictional users/drivers with plausible distinct names, unique UUIDs/licence numbers, distinct two-digit car numbers within the grid, and team memberships. Historical drivers may reuse car numbers in later races. It starts the simulator immediately and returns the same race row. Each entry receives a stable pace offset used by the simulator; telemetry positions follow lap/sector/elapsed timing. Bootstrap idempotently adds any missing pit boxes 1–4 to existing generated race events.
- `DELETE /api/demo-races/{session_id}` (admin/steward) stops its simulator and removes that generated race's PostgreSQL records and MongoDB telemetry. It returns 204. It must reject non-generated session IDs, leave seeded races untouched, and avoid deleting data shared with other sessions.
- In local Compose, `AUTO_DEMO_RACE=1` creates a running generated race on fresh startup. Active generated races restore their last recorded driver and incident state after backend/simulator restart. When an automatic race completes, its session, classification, incidents, stops and MongoDB telemetry remain archived; a new generated session starts after five seconds. With `AUTO_DEMO_RACE=0`, startup creates no race automatically. The frontend Live page lists these races and offers a one-click create/start action and a delete action. It selects a newly created race automatically. Deletion validates the generated-race and dependency guards before stopping or awaiting its simulator.
- `GET /api/sessions/{session_id}/laps` (authenticated) returns each completed driver lap once, with sector splits, plus that session's incident reports and named pit stops. Live Timing polls it every five seconds. The simulator advances each driver's sector when that driver's simulated pace reaches the next sector boundary and emits automatic reviewable incidents on selected laps of generated races.


## Race database explorer (ADMIN)
- The `/dbms` workspace groups one-click navigation for PostgreSQL overview, race archives, all 17 public base tables, EER, schema, indexes, query plans, locks, database operations, MongoDB collections, and cross-store results. PostgreSQL navigation is based on actual base tables; it does not expose public SQL `VIEW` objects. MongoDB navigation reflects the configured database's actual collections and does not assume any collection beyond telemetry. The selected view is stored in the URL hash; direct links and browser Back/Forward restore the selected view.
- `GET /api/dbms/mongo/collections` (admin) returns actual MongoDB collection names, live document counts, and index definitions. `GET /api/dbms/mongo/collections/{collection_name}` (admin) returns filtered, paged documents from a listed collection; query filters, `limit` and `offset` are applied by the API. The UI provides document filters, paging, and a raw JSON inspector. Unknown collections return 404. These endpoints do not create collections or indexes.
- GET `/api/dbms/overview`: live SQL counts for sessions, incidents, pit stops and results, plus MongoDB sample count and service state. MongoDB failure leaves SQL counts available.
- GET `/api/dbms/tables`: public PostgreSQL base-table names and live row counts. GET `/api/dbms/tables/{table_name}?limit=50&offset=0`: whitelisted, paged table rows and column names, omitting password hashes. Unknown table names return 404.
- The DBMS frontend is one navigable workspace. Its live summary polls every five seconds; active race snapshots poll every second, locks every three seconds, table rows every five seconds, other open read-only views every ten seconds, and the EER model every fifteen seconds. Write demonstrations execute only when requested and show their API outcome.
- The global Refresh action refreshes the selected race database view as well as the other active DBMS views. Table offsets are clamped to valid bounds.
- GET `/api/dbms/races`: all race sessions with event/circuit names, state, laps and timestamps. Active sessions sort first.
- GET `/api/dbms/races/{session_id}`: session context, SQL results/incidents/penalties/pit reservations, driver identities, Mongo latest sample per driver, complete deduplicated lap measurements, telemetry count and server `updated_at`. `?include_laps=false` omits the growing lap array for fast live polling and returns `laps_included:false` plus the distinct `completed_driver_laps` count. `GET /api/dbms/races/{session_id}/laps` returns `{session_id,laps,lap_source}` for the full archive. Unknown/non-race IDs return 404.
- `lap_source` is `historical_demo` for persisted fictional fixture laps, otherwise `recorded_telemetry`. Reads never generate measurements.
- Local bootstrap seeds missing Mongo lap archives only for the two exact original completed race fixtures; idempotent and preserves existing telemetry.
- UI refreshes selected active/paused/scheduled race every second with no overlapping requests; completed races retain their final snapshot. Race list refreshes every five seconds and detects lifecycle changes.
- Live Timing consumes the WebSocket session end event and preserves completion data. A race with no pit stops displays a valid zero-stop state.
- GET `/api/dbms/eer`: connected public schema columns with primary-key flags and actual FK relationships. Role specialization and external Mongo UUID links are described separately.

Generated races persist `demo_races.auto_repeat` (false for manually created generated races). Startup resumes active generated races, creates a new automatic race when enabled and none is active, and preserves completed archives across restarts.
